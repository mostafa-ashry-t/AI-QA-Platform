# Automation Execution

| Field | Value |

| Upstream | `automation-generation` (a `completed` `stage_execution` per binding; ungated) |

| Approval key | None. The stage stops after its outputs. |

```
automation/<project-dir>/ (one per binding) + generation event + approved TestCases (expected results)
        ↓  per binding, independently: preflight → run (env vars only) → collect evidence → classify
   automation-execution/results/<run-id>/<project-dir>/ + execution-metrics.json
        ↓
   automation-execution/<project-dir>/automation-report.html  (one per binding)
        ↓
   STOP → self-healing (non-passing runs, not application) → rerun here | reporting
```

## Purpose

Produce trustworthy, reproducible evidence of what the generated automation actually
did against the live application: which run passed or failed, how long it took, and
why each non-passing run did not pass. A result is claimed only when the runner's
own output shows it.

## Separation of concerns

| Concept | For this stage |
|---|---|
| **Skill** (this file) | *How* runs are prepared, executed, measured, classified, reported and journaled. |
| **Prompt** | The versioned instruction, recorded by id and version with its text in `prompts.json`. |
| **Workflow** | *When*: after `automation-generation`; again after each `self-healing` change. |
| **Journal** | *What happened*: commands (names of env vars only), outcomes, durations, evidence, classifications. |
| **Artifacts** | Run folders, `execution-metrics.json`, one HTML report per binding. |
| `automation-generation` / `self-healing` | Own the test code. This skill never edits it. |

## Trigger Conditions

Run when a human or the orchestration layer asks to run the automation of a **named
task**, optionally naming bindings and cases. If no task is named, ask. Never start
`self-healing` or `automation-generation` on its own.

## Prerequisites

| # | Prerequisite | Failure |
|---|---|---|
| 1 | `platform/tasks/<task-name>/` exists and is not under `platform/templates/` | `AE-E01` |
| 2 | `journal/workflow-run.json` → `active_run_id` is non-null (read only) | `AE-E02` |
| 3 | For each requested binding: a `completed` `automation-generation` `stage_execution` exists and its project directory exists | `AE-E03` |
| 4 | The approvals the generation rested on are still current (TestCases, TestReview, ExecutionReport hashes unchanged) | `AE-E04` |
| 5 | The binding's toolchain is available (see [Binding Runners](#binding-runners)); a JDK may be selected per command via `JAVA_HOME`, never by changing system settings | `AE-E05` |
| 6 | The credential environment variables named in `AutomationGeneration.md` §6 are present in the run environment (checked by **name**; values never read into logs) | `AE-E06` |

A failing prerequisite blocks **only that binding**: journal a `blocked`
`stage_execution` for it, report, and continue with the other bindings.
An `AE-E06` failure is reported as "credentials not provided"; the skill never
looks for credentials elsewhere (pages, files, history).

## Responsibilities

- Run each requested binding **independently**: its own working directory, command,
  toolchain and environment. No shared dependencies, outputs or commands.
- Give every command run a unique run ID: `run-<yyyymmdd>-<letter><n>` (one letter per
  binding, e.g. `A` Playwright, `B` SHAFT; `n` increases per run) or the human's ID.
- Pass credentials only as process environment variables of the test command.
- Measure: test duration and runner total from the runner's machine-readable output;
  wall-clock around the command from the shell. Unmeasured values stay null.
- Capture evidence and preserve it (see [Evidence Rules](#evidence-rules)).
- Classify every non-passing run ([Result Classification](#result-classification)).
- Scan all new outputs for credential values; redact or report, never publish.
- Write metrics, reports and journal events.

## Non-Responsibilities

- Edit test code, configuration, locators, waits, assertions or data resolvers
  (that is `self-healing`; `automation-generation` owns generation).
- Change approved artifacts, expected results, bug statuses or classifications.
- Create bug reports. A run that fails on application behavior is reported with
  failure class `application` and handed to the human for the bug process.
- Rerun to get a pass. Retries stay 0.
- Use Playwright MCP, or obtain credentials from anywhere but the environment.

## Binding Runners

Each binding is run with its own toolchain, from its own project directory.

| Binding | Toolchain check | First-run setup (once per machine/version) | Command | Machine-readable results |
|---|---|---|---|---|
| `playwright-ts` | `node -v`, `npx playwright --version` | `npm ci`; `npx playwright install <browser>` (build must match the pinned version) | `npx playwright test` (filter: `--grep @TC-###`) | `results.json`, `junit.xml`, `html-report/` in the run folder |
| `shaft-java-testng` | `$JAVA_HOME/bin/javac -version` (JDK at the project's Java level), `mvn -v` | First `mvn test-compile` downloads dependencies; SHAFT downloads its Allure CLI on first run | `mvn test` (plus `-Dshaft.extraArgLine=-Duser.home=<path without spaces>` when the profile path contains a space) | `target/surefire-reports/testng-results.xml`, `allure-results/`, `allure-report/*_AllureReport.html` (copied into the run folder) |
| `playwright-java-testng` | JDK + `mvn -v` | First `mvn test-compile` | `mvn test` | `target/surefire-reports/` |

Every command sets `QA_RUN_ID=<run-id>` so the generated code writes its evidence to
`automation-execution/results/<run-id>/<project-dir>/`. Discovery-only commands use
a reporter that writes nothing (e.g. `npx playwright test --list --reporter=list`).

## Execution Procedure

Per binding:

1. **Preflight** (no application access): prerequisites; toolchain versions recorded;
   static discovery lists exactly the expected case IDs.
2. **Run** the command once with retries 0, wrapped in a wall-clock timer; save the
   console output to `<run folder>/console.log` (Playwright) or
   `maven-console.log` (Maven).
3. **Collect** runner outputs into the run folder (copy, don't move, for tools that
   write inside the project, e.g. SHAFT's `allure-results/` and report).
4. **Extract** metrics from the machine-readable outputs and the step log.
5. **Classify** the outcome and, for non-passing runs, the failure class.
6. **Secret scan** of the new run folder, including zip members (traces).
7. Continue with the next binding. One binding's failure never stops another.

## Rerun Policy

- Do not rerun a passing binding unless the human asks (e.g. a stability series of
  *n* runs, recorded as such).
- After a `self-healing` change, rerun **only** the affected binding and cases, once,
  as a new run ID that cites the healing ID.
- Never overwrite or reuse a run folder.

## Result Classification

| Outcome | Meaning |
|---|---|
| `passed` | All selected tests passed **and** the command succeeded |
| `failed` | At least one test failed |
| `not_run` | No test started (setup, toolchain, configuration) |
| `harness_failed` | Tests ran, but the runner or build failed afterwards. Never counted as a pass, even if every test passed |

Failure class (first match wins, each backed by cited evidence):

| Class | Typical evidence |
|---|---|
| `environment` | Missing browser/driver/JDK, network or site unavailable, path problems |
| `configuration` | Framework or build configuration error before/after tests |
| `framework_defect` | Failure inside the framework's own code (stack frames in framework packages) |
| `test_data` | `[TEST DATA] test data not available: DATA-###` |
| `test_script` | Locator, wait or plumbing in the generated code does not match the observed, approved behavior |
| `application` | The approved expected result is not met while the steps were performed as written (assertion message `<case> expected: …` with real values) |
| `unknown` | Evidence insufficient; say what is missing |

A failure with class `application` is reported, never healed.

## Evidence Rules

- Kept per run: step log, final or failure screenshot, trace (Playwright, steps after
  secret entry only), native report, machine-readable results, console log, fork dumps.
- Evidence IDs (`EVD-###`) continue the task-wide sequence; each journaled item has
  path, SHA-256 and capture time.
- Never edit, crop or delete evidence. Redact a secret found by the scan as
  `[REDACTED: credential]` in a copy, and record the redaction.

## Reporting

`automation-report.html` per binding follows
[`automation-report.structure.md`](automation-report.structure.md): self-contained
(inline CSS/JS, base64 images), numbers read from `execution-metrics.json` and the run
outputs, relative links to native reports and evidence, a footer stating that no
credentials are stored. Comparisons between bindings belong to `reporting`.

## Validation Rules (self-checks before presenting)

| Check | Rule |
|---|---|
| AE-V01 | Prerequisites checked per binding before any run |
| AE-V02 | Every run has a unique run ID and folder; no folder reused |
| AE-V03 | Every reported outcome and duration comes from runner output or the shell timer |
| AE-V04 | Every non-passing run has an outcome, a failure class and cited evidence |
| AE-V05 | `execution-metrics.json` validates against its schema |
| AE-V06 | Secret scan of new outputs: 0 credential values |
| AE-V07 | Test code and approved artifacts unchanged by this stage (hashes before = after) |
| AE-V08 | Each HTML report parses, its relative links resolve, and it contains no credential or e-mail address |

## Failure Conditions

| Code | Condition | Event status |
|---|---|---|
| AE-E01 – AE-E06 | Prerequisites | `blocked` (that binding only) |
| AE-E07 | Runner could not be started at all (command missing) | `failed` |
| AE-E08 | Credential value found in an output and cannot be redacted | `failed`; output withheld from reports |

Non-passing test runs are **results**, not stage failures: the event is `completed`.

## Journal Integration

One `stage_execution` per binding per request, `status: completed` (or
`blocked` / `failed`), `approval_required: false`, with: `automation_runs` (schema
1.7.0; one entry per run), `test_results` (per case: `PASS` only for a `passed` run;
otherwise `BLOCKED` or `FAIL` with `failure_cause`), `environment`, `browser`,
`evidence`, `output_artifacts` (metrics, report), `validation`. Commands list env var
**names** only.

## Hand-off to Self-Healing

For each non-passing run with class other than `application`, hand over: run ID,
binding, failure class, error excerpt, evidence paths. Self-healing returns with a
healing ID and asks for one verification rerun of the affected binding.

## Stop Behavior

Present per binding: runs, outcomes, durations, failure classes, evidence and report
paths, healing hand-offs. Then STOP.
