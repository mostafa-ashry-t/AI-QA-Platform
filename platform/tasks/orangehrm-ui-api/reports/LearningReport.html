1. Overview·1. نظرة عامة

The AI QA Platform is a reusable, AI-assisted QA testing platform. It is not a test project for one application: OrangeHRM (the public demo site, Directory UI) is only its first validation project. Work is organised as a workflow of stages, each implemented by its own skill and each writing its artifacts into the task folder:

PRD → Project Context → Exploration → Test Design → Test Review (mandatory, ADR-001) → Manual Execution → Automation Generation → Automation Execution → Self-healing (when needed) → Reporting.

Gated stages stop after producing their artifact; only an exact approval key (for example TEST_REVIEW_APPROVED, MANUAL_EXECUTION_APPROVED) unlocks the next stage. Before this milestone the task had: Test Design v1.4.0 with 58 cases, Test Review v1.3.0, and Manual Execution with 40 PASS, 0 FAIL, 0 BLOCKED and 18 Exploratory cases observed (MANUAL_EXECUTION_APPROVED, journal event EVT-0043). Bug reports BUG-001 – BUG-005 are Suspected/Open; this milestone added none.

TC-054 is the only case with Needs Automation = TRUE (human decision, journal EVT-0017). It is an end-to-end flow: log in through the redirect, filter the Directory by Job Title and Location, open and close an employee's detail panel, click Reset, and check that the page returns to its default, unfiltered state.

Why two frameworks? The human decided on 2026-10-18 to implement TC-054 in two independent frameworks and compare them: Framework A, Playwright + TypeScript (named in the task's PRD/Project Context), and Framework B, SHAFT Engine + Selenium + Java 21 + TestNG + Maven (the platform's Tooling Rule for automation). Both implement the same approved steps with the same assertions, so the comparison isolates the framework.

This milestone is recorded in the task journal as EVT-0044 (automation-generation, playwright-ts), EVT-0045 (automation-generation, shaft-java-testng), EVT-0046 (automation-execution, Playwright A1–A6), EVT-0047 (automation-execution, SHAFT B1–B6) and EVT-0048 (self-healing: E-001, H-001 – H-003). The automation-generation skill and prompt are at v1.1.0.

منصة ضمان الجودة بالذكاء الاصطناعي منصة اختبار قابلة لإعادة الاستخدام تعمل بمساعدة الذكاء الاصطناعي، وليست مشروع اختبار لتطبيق واحد؛ فتطبيق OrangeHRM (موقع العرض العام، واجهة Directory) هو أول مشروع للتحقق منها فقط. يُنظَّم العمل في سير عمل من مراحل، تنفّذ كلَّ مرحلة مهارةٌ (skill) مستقلة، وتكتب كلُّ مرحلة مخرجاتها داخل مجلد المهمة:

حالة الاختبار TC-054 هي الحالة الوحيدة التي قيمة Needs Automation فيها TRUE (قرار بشري، الحدث EVT-0017). وهي تدفق من البداية إلى النهاية: تسجيل الدخول عبر إعادة التوجيه، ثم تصفية صفحة Directory حسب Job Title وLocation، ثم فتح لوحة تفاصيل موظف وإغلاقها، ثم النقر على Reset، والتحقق من أن الصفحة عادت إلى حالتها الافتراضية غير المصفّاة.

2. The test case — TC-054·2. حالة الاختبار TC-054

Source: test-design/TestCases.md v1.4.0, section “TC-054 — End-to-end: redirect login, combined filter, employee details, close, Reset”. Type: End-to-End. Priority: High. Test data: DATA-001 (demo account), DATA-012 (a Job Title + Location pair). The text below is quoted verbatim.

PreconditionsNo authenticated session in the browser (fresh browser context, or logged out).
Step 1Open the Directory URL and log in with the demo account (DATA-001).
Step 2Select the Job Title and the Location of the DATA-012 pair; click Search.
Step 3Wait until result cards are displayed; read the results header and note the filtered record count k ("(k) Records Found", or "(1) Record Found" when k is 1).
Step 4Click the first result card; then click the panel's arrow icon.
Step 5Click Reset.
Step 6Wait until employee result cards are displayed, then read the results header.
Expected ResultEmployee Name is empty, Job Title and Location display "-- Select --", and the results header reads "(N) Records Found" with N greater than the count k noted in step 3.

Why it is “data-aware”. The demo site is shared and its data changes during a session. So the case uses no fixed employee names or totals: DATA-012 is read at run time from the first displayed card that shows both a job title and a location, k and N are both read in the same run, and only N > k is asserted. The header is read only after cards are displayed, because a transient “No Records Found” was seen once while the list loaded (PB-001).

المصدر: test-design/TestCases.md الإصدار v1.4.0. النوع: من البداية إلى النهاية (End-to-End). الأولوية: عالية. بيانات الاختبار: DATA-001 (حساب العرض التجريبي) وDATA-012 (زوج من Job Title وLocation).

ترجمة — النص الإنجليزي أعلاه هو النص المعتمد

الشروط المسبقةلا توجد جلسة مصادَق عليها في المتصفح (سياق متصفح جديد، أو بعد تسجيل الخروج).
الخطوة 1افتح رابط صفحة Directory وسجّل الدخول بحساب العرض التجريبي (DATA-001).
الخطوة 2اختر قيمتَي Job Title وLocation الخاصتين بالزوج DATA-012، ثم انقر Search.
الخطوة 3انتظر حتى تظهر بطاقات النتائج؛ اقرأ عنوان النتائج وسجّل عدد السجلات بعد التصفية k ("(k) Records Found"، أو "(1) Record Found" عندما تساوي k واحدًا).
الخطوة 4انقر أول بطاقة نتيجة، ثم انقر أيقونة السهم في اللوحة.
الخطوة 5انقر Reset.
الخطوة 6انتظر حتى تظهر بطاقات نتائج الموظفين، ثم اقرأ عنوان النتائج.
النتيجة المتوقعةيكون حقل Employee Name فارغًا، ويعرض كلٌّ من Job Title وLocation النص "-- Select --"، ويكون عنوان النتائج "(N) Records Found" حيث N أكبر من العدد k المسجَّل في الخطوة 3.

لماذا هي «مراعية للبيانات»؟ موقع العرض مشترك وبياناته تتغير أثناء الجلسة؛ لذلك لا تستخدم الحالة أسماء موظفين أو أعدادًا ثابتة: يُقرأ DATA-012 وقت التشغيل من أول بطاقة معروضة تُظهر مسمّى وظيفيًا وموقعًا معًا، ويُقرأ كلٌّ من k وN في التشغيل نفسه، ولا يُؤكَّد إلا الشرط N > k. ولا يُقرأ العنوان إلا بعد ظهور البطاقات، لأن رسالة «No Records Found» عابرة ظهرت مرة واحدة أثناء تحميل القائمة (PB-001).

3. Framework A explained — Playwright + TypeScript·3. شرح الإطار A — Playwright مع TypeScript

Stack: Playwright 1.64.1 + TypeScript 5.9.3 + Playwright Test, Node 24.19.0, Chromium headless shell 156.0.8078.4 (build 1248). Project folder: automation/playwright-ts/. Direct dependencies: @playwright/test, typescript, @types/node.

The layout is config → page objects → one test: config.ts reads every setting from environment variables, the qa fixture handles step logging, tracing and evidence, two page objects hold the locators, and TC-054.spec.ts labels each step with the approved text verbatim.

التقنيات: Playwright 1.64.1 مع TypeScript 5.9.3 وPlaywright Test، وNode 24.19.0، ومتصفح Chromium بلا واجهة 156.0.8078.4 (البناء 1248). مجلد المشروع: automation/playwright-ts/. الاعتماديات المباشرة: @playwright/test وtypescript و@types/node.

البنية هي إعدادات ← نماذج كائنات الصفحات ← اختبار واحد: يقرأ config.ts كل إعداد من متغيرات البيئة، وتتولى تجهيزة qa (fixture) تسجيل الخطوات والتتبّع والأدلة، ويحتفظ نموذجا الصفحتين بمحددات العناصر، ويضع TC-054.spec.ts نص كل خطوة معتمدة حرفيًا كعنوان لها.

Configuration·الإعدادات

Retries are 0 and there is one worker, so every failure is reported as it happened. Screenshots and tracing are off in the config on purpose: the fixture controls them so that the login step is never recorded. Four reporters write the list output, the HTML report, results.json and junit.xml into the run folder.

عدد مرات إعادة المحاولة 0 ويوجد عامل (worker) واحد، فيُبلَّغ عن كل فشل كما حدث. لقطات الشاشة والتتبّع معطّلة في الإعدادات عن قصد، لأن التجهيزة هي التي تتحكم فيهما حتى لا تُسجَّل خطوة تسجيل الدخول أبدًا. وتكتب أربعة مُبلِّغات (reporters) المخرجات النصية وتقرير HTML وresults.json وjunit.xml في مجلد التشغيل.

Secrets: credentials only from the environment·الأسرار: بيانات الدخول من البيئة فقط

No credential value exists in the project. If QA_USERNAME or QA_PASSWORD is missing, the run fails fast with a [CONFIGURATION] message, which cannot be confused with an assertion failure.

لا توجد أي قيمة لبيانات الدخول داخل المشروع. إذا غاب QA_USERNAME أو QA_PASSWORD يفشل التشغيل فورًا برسالة [CONFIGURATION]، ولا يمكن خلطها بفشل تأكيد.

The fixture: tracing starts after the login·التجهيزة: يبدأ التتبّع بعد تسجيل الدخول

A Playwright trace records DOM snapshots and network traffic, so a traced login would capture typed secrets. The test therefore calls startTracing() only after step 1. At the end, the fixture always writes a full-page screenshot (final.png on pass, failure.png on failure) and saves trace.zip only when the test failed.

يسجّل تتبّع Playwright لقطات من DOM وحركة الشبكة، لذا فإن تتبّع خطوة الدخول سيلتقط الأسرار المكتوبة. ولهذا لا يستدعي الاختبار startTracing() إلا بعد الخطوة 1. وفي النهاية تكتب التجهيزة دائمًا لقطة شاشة للصفحة كاملة (final.png عند النجاح، وfailure.png عند الفشل)، ولا تحفظ trace.zip إلا عند فشل الاختبار.

Page object: waits without sleeps·نموذج الصفحة: انتظار بلا توقّف ثابت

Playwright actions wait automatically for their element, and expect(locator) assertions retry until the timeout (30 000 ms by default here). One retrying assertion, not.toHaveText(previous), expresses “wait until the header changes” after Search or Reset. There are no fixed sleeps and no networkidle. Note the comment about healing H-001 on the header regex (section 8).

تنتظر إجراءات Playwright عناصرها تلقائيًا، وتعيد تأكيدات expect(locator) المحاولة حتى انتهاء المهلة (30 000 ملّي ثانية افتراضيًا هنا). ويعبّر تأكيد واحد يعيد المحاولة، وهو not.toHaveText(previous)، عن «انتظر حتى يتغير العنوان» بعد Search أو Reset. لا توجد فترات توقف ثابتة ولا networkidle. لاحظ التعليق الخاص بالإصلاح H-001 على التعبير النمطي للعنوان (القسم 8).

Assertions: the approved expected result, in five soft parts·التأكيدات: النتيجة المتوقعة المعتمدة في خمسة أجزاء مرنة

expect.soft reports every part even if one fails, so a single run shows the whole state after Reset. Each message starts with “TC-054 expected:” so a failure points straight back to the approved text.

يُبلِّغ expect.soft عن كل جزء حتى لو فشل أحدها، فيُظهر تشغيل واحد الحالة الكاملة بعد Reset. وتبدأ كل رسالة بـ “TC-054 expected:” بحيث يشير أي فشل مباشرة إلى النص المعتمد.

Maven, TestNG and SHAFT properties·إعدادات Maven وTestNG وخصائص SHAFT

Surefire runs the TestNG suite with SHAFT's listener and never reruns a failed test. The rp.enable=false system property and the empty-by-default shaft.extraArgLine are the two framework fixes H-002 and H-003 (section 8). In custom.properties, retries are 0 and SHAFT's “click with JavaScript when the normal click fails” fallback is off, so a failure surfaces instead of being worked around.

يشغّل Surefire مجموعة TestNG مع مستمع (listener) SHAFT ولا يعيد تشغيل أي اختبار فاشل. خاصية النظام rp.enable=false والخاصية shaft.extraArgLine (فارغة افتراضيًا) هما إصلاحا الإطار H-002 وH-003 (القسم 8). وفي custom.properties عدد مرات إعادة المحاولة 0، والبديل «النقر عبر JavaScript إذا فشل النقر العادي» معطّل، حتى يظهر الفشل بدل الالتفاف عليه.

Browser lifecycle and evidence (BaseTest)·دورة حياة المتصفح والأدلة (BaseTest)

Secrets: typeSecure·الأسرار: typeSecure

typeSecure types the value but shows the step as “Type securely” with the value masked in the Allure report. The values themselves come from Config.username() / Config.password(), which read the environment variables QA_USERNAME / QA_PASSWORD and fail with [CONFIGURATION] when they are missing.

يكتب typeSecure القيمة لكنه يعرض الخطوة في تقرير Allure باسم «Type securely» مع إخفاء القيمة. وتأتي القيم نفسها من Config.username() وConfig.password() اللذين يقرآن متغيري البيئة QA_USERNAME وQA_PASSWORD، ويفشلان برسالة [CONFIGURATION] عند غيابهما.

Waits: SHAFT element waits + explicit WebDriverWait·الانتظار: انتظار عناصر SHAFT مع WebDriverWait الصريح

SHAFT element actions (driver.element().click(...)) wait for their element up to defaultElementIdentificationTimeout. Conditions about page state — “the header changed”, “the panel is hidden” — need explicit Selenium WebDriverWait lambdas. The logic is identical to Framework A: header-change wait, then cards visible, then the count pattern. Because the header text is trimmed before parsing, Framework B was not affected by the whitespace problem H-001.

تنتظر إجراءات عناصر SHAFT (driver.element().click(...)) العنصرَ حتى defaultElementIdentificationTimeout. أما الشروط المتعلقة بحالة الصفحة، مثل «تغيّر العنوان» و«اختفت اللوحة»، فتحتاج إلى دوال lambda صريحة مع WebDriverWait من Selenium. المنطق مطابق للإطار A: انتظار تغيّر العنوان، ثم ظهور البطاقات، ثم نمط العدد. ولأن نص العنوان يُقصّ (trim) قبل تحليله، لم يتأثر الإطار B بمشكلة المسافة H-001.

Assertions: SHAFT validations (hard)·التأكيدات: تحققات SHAFT (صارمة)

SHAFT.Validations.assertThat()…perform() is a hard assertion: it stops at the first failing part (unlike Playwright's expect.soft). The five checks and their messages are the same as in Framework A. Every SHAFT action and validation appears as a step in the Allure report automatically; the approved step labels are logged via SHAFT.Report.log.

SHAFT.Validations.assertThat()…perform() تأكيد صارم يتوقف عند أول جزء فاشل (بخلاف expect.soft في Playwright). الفحوص الخمسة ورسائلها هي نفسها في الإطار A. ويظهر كل إجراء وكل تحقق من SHAFT تلقائيًا كخطوة في تقرير Allure، وتُسجَّل عناوين الخطوات المعتمدة عبر SHAFT.Report.log.

5. Execution·5. التنفيذ

How to run

Conclusions — measured [M]

  • Both frameworks implement TC-054 completely and pass it 4 out of 4 times after their fixes, with the same data, the same synchronization design and the same assertions.

Conclusions — qualitative [Q]

  • For this project Playwright + TypeScript gave faster feedback and the better debugging tools (trace viewer, precise assertion errors).
  • SHAFT + Java fits the platform's Java/TestNG stack and produces a richer report out of the box (every action logged, secrets masked automatically), at the cost of a heavier toolchain and less transparent failures inside the framework.
  • Neither result is a general ranking: it rests on one test case, one machine and four runs per framework.

No assertion was changed — and why that matters. Totals: 4 interventions (1 environment, 1 test-script defect, 2 framework configuration / framework defect), 0 application defects, 0 assertions or expected results changed. A test exists to detect when the application stops behaving as approved. If a fix edits the expected value to match whatever the screen shows, the test turns green but no longer tests anything — a real defect would be “healed” away silently. Here every fix touched only waits, setup or tooling, the approved TestCases v1.4.0 stayed hash-identical, and the same five assertions decided every pass.

لم يُغيَّر أي تأكيد، ولماذا هذا مهم. الإجمالي: 4 تدخلات (1 بيئة، و1 عيب في السكربت، و2 إعدادات/عيب في الإطار)، و0 عيوب في التطبيق، و0 تأكيدات أو نتائج متوقعة تم تغييرها. يوجد الاختبار ليكشف متى يتوقف التطبيق عن التصرف كما هو معتمد. فإذا عدّل الإصلاحُ القيمةَ المتوقعة لتطابق ما تعرضه الشاشة، يصبح الاختبار أخضر لكنه لم يعد يختبر شيئًا، وقد «يُصلَح» عيب حقيقي ويختفي بصمت. هنا لم يمسّ أي إصلاح إلا الانتظار أو التهيئة أو الأدوات، وبقي ملف TestCases المعتمد v1.4.0 مطابقًا ببصمة التجزئة (hash)، وحسمت التأكيدات الخمسة نفسها كل نجاح.

9. Lessons learned·9. الدروس المستفادة

  1. [M] Pin the framework and install its browser build. Playwright 1.64.1 needs Chromium build 1248; with only older builds cached, A1 failed after 2 ms. Make npx playwright install chromium part of first-run setup.
  2. [M] A regex on raw DOM text sees whitespace. toHaveText(RegExp) received " (111) Records Found"; the anchored pattern failed for 30 s although the right element was found 62 times. Trim before matching, or allow \s* in waits.
  3. [M] Framework internals can fail the build. In B1 SHAFT's listener crashed before any test; in B2 the test passed in TestNG but the build failed and Surefire reported Tests run: 0. Always check both the test result and the build result.
  4. [M] Paths with spaces still break tools. An unquoted user.home path broke Allure generation. Fix it with an optional, empty-by-default property instead of hard-coding a machine path into the project.
  5. [M] Use data-aware assertions on shared data. N moved between 105 and 111 during the session. Reading k and N in the same run and asserting only N > k kept all 8 passing runs stable without fixed counts.
  6. [M] Never trace or log secrets. The Playwright login step is not traced; SHAFT types with typeSecure; credentials come only from QA_USERNAME / QA_PASSWORD. Secret scan: 149 files + 105 zip members, 0 hits.
  7. [M] Retries 0 and no fixed sleeps. Both projects ran with 0 retries and 0 sleeps; failures surfaced as they were, and there were no flaky results in 4 runs per framework after the fixes.
  8. [M] Check version constraints before choosing a release. SHAFT 10.1.20260123 is the newest release for Java 21; later releases require JDK 25.
  9. [Q] Transparent failures save time. H-001 was diagnosed from the Playwright error alone; H-002 and H-003 needed fork dumps and byte-code inspection.
  10. Label non-assertion failures. [TEST DATA] and [CONFIGURATION] errors can never be mistaken for a failed expected result.
  11. [M] Measure honestly. Four passing runs per framework on one machine are indicative, not a benchmark — say so next to the numbers.
  1. [M] ثبّت إصدار الإطار وثبّت بناء المتصفح الخاص به. يحتاج Playwright 1.64.1 إلى البناء 1248 من Chromium؛ ومع وجود بناءات أقدم فقط فشل A1 بعد 2 ملّي ثانية. اجعل npx playwright install chromium جزءًا من تهيئة التشغيل الأول.
  2. [M] التعبير النمطي على نص DOM الخام يرى المسافات. استلمت toHaveText(RegExp) النص " (111) Records Found"، ففشل النمط المثبَّت لمدة 30 ثانية رغم العثور على العنصر الصحيح 62 مرة. قُصّ النص قبل المطابقة، أو اسمح بـ \s* في الانتظار.
  3. [M] قد تُفشل مكوّنات الإطار الداخلية عملية البناء. في B1 انهار مستمع SHAFT قبل أي اختبار، وفي B2 نجح الاختبار في TestNG لكن فشل البناء وأبلغ Surefire عن Tests run: 0. افحص دائمًا نتيجة الاختبار ونتيجة البناء معًا.
  4. [M] المسارات التي تحتوي مسافات ما زالت تُعطّل الأدوات. مسار user.home غير المقتبس عطّل توليد Allure. عالج ذلك بخاصية اختيارية فارغة افتراضيًا بدل تثبيت مسار خاص بالجهاز في المشروع.
  5. [M] استخدم تأكيدات مراعية للبيانات مع البيانات المشتركة. تغيّر N بين 105 و111 أثناء الجلسة. قراءة k وN في التشغيل نفسه وتأكيد N > k فقط أبقيا التشغيلات الناجحة الثمانية مستقرة دون أعداد ثابتة.
  6. [M] لا تتتبّع الأسرار ولا تسجّلها أبدًا. خطوة الدخول في Playwright غير متتبَّعة، وSHAFT يكتب عبر typeSecure، وبيانات الدخول تأتي من QA_USERNAME وQA_PASSWORD فقط. فحص الأسرار: 149 ملفًا و105 عناصر zip، ونتيجة 0.
  7. [M] صفر إعادة محاولة وبلا توقف ثابت. عمل المشروعان بـ 0 إعادة محاولة و0 توقف ثابت؛ ظهرت الأعطال كما هي، ولم تظهر نتائج متذبذبة في 4 تشغيلات لكل إطار بعد الإصلاح.
  8. [M] تحقّق من قيود الإصدارات قبل اختيار الإصدار. الإصدار 10.1.20260123 هو أحدث إصدار من SHAFT لـ Java 21، والإصدارات اللاحقة تتطلب JDK 25.
  9. [Q] الأعطال الواضحة توفّر الوقت. شُخِّص H-001 من رسالة خطأ Playwright وحدها، بينما احتاج H-002 وH-003 إلى ملفات dump وفحص الكود الثنائي.
  10. ميّز الأعطال التي ليست فشل تأكيد. أخطاء [TEST DATA] و[CONFIGURATION] لا يمكن خلطها بفشل النتيجة المتوقعة.
  11. [M] قِس بأمانة. أربعة تشغيلات ناجحة لكل إطار على جهاز واحد نتيجة استرشادية لا معيارية، فاذكر ذلك بجانب الأرقام.

Fixtureتجهيزة الاختبار (Fixture)Setup/teardown code that Playwright Test provides to a test (here the qa fixture).
Auto-waitingالانتظار التلقائيThe framework waits for an element to be ready before acting on it.
Explicit waitانتظار صريحA coded wait for a specific condition, e.g. Selenium WebDriverWait.

Traceالتتبّع (Trace)Playwright's recording of DOM snapshots, network and actions (trace.zip).
Regular expression (regex)تعبير نمطيA text pattern; anchored with ^ and $ it must match the whole text.
Test dataبيانات الاختبارInputs a test needs (DATA-001, DATA-012).

Environment variableمتغير بيئةA value supplied by the shell or IDE (QA_USERNAME, QA_PASSWORD), never stored in code.

Headless browserمتصفح بلا واجهةA browser that runs without a visible window.
