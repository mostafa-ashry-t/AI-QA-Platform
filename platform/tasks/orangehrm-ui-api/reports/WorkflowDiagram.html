0. Reusable architecture — what is shared and what belongs to one task

The platform is not a test project for one application. Everything on the left is project-agnostic and reused by every task; everything specific to OrangeHRM lives in the task folder on the right, starting from context/TaskContext.md. A new project is started by copying the template into platform/tasks/<task-name>/ and filling TaskContext.md — no skill, prompt, workflow or schema changes.

On narrow screens, scroll the diagram sideways.

How one stage runs (common to every skill)

  1. Prerequisites: the skill checks that every upstream approval it depends on exists in the journal and is still current (artifact SHA-256 unchanged, no later re-run). If not, it journals a blocked event and stops.
  2. Inputs: only approved artifacts of this task, TaskContext.md identity, and the active workflow_run_id (read only).
  3. Output: exactly its own artifact(s) in its own stage folder, from the skill's template; revisions update the same file in place.
  4. Self-validation against the skill's rules, then a journal event (schema-validated) and the prompt snapshot in prompts.json.
  5. Gate: gated stages stop. Only the exact standalone key (e.g. TEST_REVIEW_APPROVED) unlocks the next stage; it is journaled as an approval_decision bound to the artifact's hash, and any later edit makes it stale.
